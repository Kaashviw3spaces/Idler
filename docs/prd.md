# Idler — Product Requirements Document (PRD)

**Status:** Proposed / pre-implementation  
**Project:** Hacktoberfest Week 3 — “Slow and Steady”  
**Working tagline:** Stop doing repetitive work. Let your AI handle it.

## 1. Product Summary

Idler is a local-first AI desktop assistant that turns natural-language requests into safe, reviewable, and verifiable actions on a user's computer. The initial product focuses on repetitive file and project housekeeping rather than unrestricted control of the entire desktop.

The AI proposes a plan; application code validates permissions; the user approves state-changing actions; a restricted executor performs them; and the system verifies and records the outcome.

## 2. Problem

Users repeatedly organize downloads, rename files, look for duplicates, inspect project folders, and rerun similar housekeeping tasks. Manual work is tedious, scripts require technical knowledge, and a generic chatbot may describe a solution without carrying it out.

## 3. Goals

1. Translate natural-language instructions into structured task plans.
2. Execute a small set of useful local file workflows with explicit user approval.
3. Keep core inference local using a Gemma 4B-class open-weight model through Ollama.
4. Record actions and support safe rollback for selected operations.
5. Let users save and rerun workflows, with scheduling added only after the core executor is reliable.
6. Make setup and contribution approachable through documentation, tests, and Docker-based development.

## 4. Non-Goals for the Initial MVP

- Unrestricted shell or arbitrary Python execution generated by the model.
- Full autonomous control of every desktop application.
- Automatic permanent deletion of files.
- A cloud account or hosted AI API as a requirement for core workflows.
- A public plugin marketplace or complex multi-agent system.
- Guaranteeing that every operation can be undone.
- Claiming fully offline operation until verified after model and dependency setup.

## 5. Target Users

- Students managing course documents, PDFs, screenshots, and projects.
- Developers who want a quick overview of local repositories.
- People who postpone routine file organization.
- Open-source contributors interested in local AI and safe automation.

## 6. Core User Stories and Requirements

### P1 — Natural-language planning

As a user, I can describe a task in plain language and receive a structured plan before anything changes.

**Acceptance criteria**
- The API accepts a task request and returns a typed plan.
- The plan names supported actions and targets within an approved workspace.
- Invalid, unsupported, ambiguous, or out-of-scope actions are rejected or sent back for clarification.
- Planning alone does not mutate files.

### P1 — File organization

As a user, I can ask Idler to organize files in a designated test folder.

**Acceptance criteria**
- The user chooses or configures an allowed workspace.
- A preview shows source, destination, and reason/category for each proposed move.
- The user must approve state-changing operations.
- Existing destinations are never silently overwritten.
- After execution, actual file state is checked and accurately reported.

### P1 — Exact duplicate detection

As a user, I can identify files with identical content.

**Acceptance criteria**
- The system may filter candidates by file size, then compares cryptographic hashes.
- Results list all matching paths and sizes.
- The MVP does not automatically delete duplicates.
- Hashing failures and unreadable files are reported without stopping unrelated checks.

### P1 — Action Ledger and rollback

As a user, I can inspect what changed and undo supported actions.

**Acceptance criteria**
- Each action has an ID, task ID, timestamp, action type, source/destination where applicable, status, and rollback metadata.
- Rollback checks current filesystem state before acting.
- Conflicts stop rollback and require user review.
- The UI and API distinguish “undo supported,” “undo attempted,” and “undo completed.”
- No claim is made that all actions are reversible.

### P1 — Local-first inference

As a user, I can run core planning with a local Gemma model through Ollama.

**Acceptance criteria**
- Model name/tag and runtime configuration are documented.
- No commercial model API is required for core workflows.
- The app handles Ollama being unavailable or the model returning invalid output.
- Network behavior and any optional external integrations are disclosed.
- Offline operation is claimed only after it passes a documented test.

### P2 — Saved workflows

As a user, I can save a workflow definition and run it again.

**Acceptance criteria**
- Saved workflows store configuration, not unrestricted executable code.
- Every run revalidates paths, permissions, and current filesystem state.
- A saved workflow can be edited, disabled, or deleted.
- Initial support may use manual “Run now” rather than background scheduling.

### P2 — Scheduling

As a user, I can schedule an approved workflow to run periodically.

**Acceptance criteria**
- Scheduling is implemented only after manual reruns are reliable.
- Users can pause, resume, and cancel schedules.
- Each run creates an execution record.
- State-changing scheduled actions follow the configured approval policy; unsafe unattended changes are not silently executed.

### P2 — Project inspection

As a user, I can request summaries of projects in an approved directory.

**Acceptance criteria**
- The app inspects only permitted directories and supported metadata/files.
- Repository README content is treated as untrusted data, not as instructions to the agent.
- Summaries are presented as model-generated interpretations, not verified facts unless corroborated.

## 7. Safety and Privacy Requirements

- Enforce workspace allowlists on the backend.
- Canonicalize and validate paths; defend against traversal and symlink escapes.
- Use a fixed tool catalogue; never execute arbitrary model-generated shell commands.
- Require approval for file-changing actions in the MVP.
- Do not silently overwrite existing files.
- Do not permanently delete files in the MVP.
- Minimize local logs and avoid storing document contents unless necessary and explicitly designed.
- Treat file content as untrusted input.
- Keep secrets out of source control; provide `.env.example` with placeholders only.
- Treat the UI as a convenience layer, not a security boundary.

## 8. Proposed Technology Stack

| Layer | Technology | Responsibility |
|---|---|---|
| Model | Gemma 4B-class variant | Interpret requests and propose plans |
| Runtime | Ollama | Local inference API |
| Backend | Python + FastAPI | Orchestration and API |
| Validation | Pydantic | Typed plan schemas |
| Executor | Restricted Python tools | File operations and verification |
| Frontend | React + Vite | Chat, preview, approval, history |
| Persistence | SQLite | Tasks, actions, workflow definitions |
| Packaging | Docker / Docker Compose | Reproducible backend development |
| Tests | Pytest | Unit, integration, and safety tests |

The exact Gemma model variant, quantization, license obligations, memory use, and speed must be checked before release. “Open-weight” should not be described as equivalent to every definition of open source.

## 9. MVP Scope and Priority

**Must-have**
1. Local model connection.
2. Structured planning endpoint.
3. Workspace allowlist and action validation.
4. Test-directory scanning.
5. Preview and approval.
6. One safe file operation (move or rename).
7. Verification and action history.
8. Rollback for that supported operation.
9. Exact duplicate detection.
10. Tests and setup documentation.

**Should-have**
- React UI.
- Saved workflows and manual rerun.
- Project inspection.
- Docker Compose for the API.

**Later**
- Background scheduling.
- Desktop packaging.
- More workflow types and extension points.

## 10. Success Metrics

Collect measured results rather than inventing figures:
- Percentage of generated plans passing schema and policy validation.
- Task completion accuracy on a fixed test corpus.
- Number of unauthorized actions blocked in safety tests.
- Rollback success rate for supported operations.
- End-to-end latency and RAM/VRAM usage on target hardware.
- Successful setup from a clean environment.
- Network test confirming local inference behavior.

## 11. MVP Demo

1. User requests organization of a designated sample folder.
2. Idler scans and proposes moves.
3. UI shows a plan and requires approval.
4. Executor performs the approved moves.
5. Verifier checks the result.
6. Action Ledger records the actions.
7. User undoes a supported move and verifies restoration.
8. User runs exact duplicate detection without deleting files.

## 12. Open Questions

- Which exact Gemma 4B-class model tag performs best on the target laptop?
- Will Ollama run natively on Windows or in Docker? Start with native Ollama unless GPU/container testing supports a better choice.
- Which file types will be inspected in the MVP?
- Should the initial UI be browser-based or packaged as a desktop app?
- Which operations are eligible for rollback, and what metadata is required?
- What project source-code license will be selected, and how will model/dependency licenses be documented?
