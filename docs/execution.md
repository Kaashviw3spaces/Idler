# Idler — Execution Plan

**Purpose:** Turn the concept into a working, testable Hacktoberfest MVP.  
**Status:** Proposed work plan; no phase should be marked complete until its acceptance criteria pass.

## Working Rules

1. Work in a dedicated repository and use a dedicated sample workspace for early tests.
2. Do not run file-changing tests against personal folders.
3. Never execute arbitrary shell commands or code generated by the model.
4. Keep changes small, test each phase, and record decisions in the README.
5. Treat model output as untrusted input.
6. Measure model speed and memory instead of making assumptions.
7. Do not claim a feature is complete until its acceptance criteria are verified.

## Phase 0 — Repository and Environment

**Tasks**
- Create repository and baseline README.
- Add `.gitignore`, `.env.example`, license placeholder/decision, and documentation folder.
- Create Python virtual environment and install FastAPI, Uvicorn, Pydantic, HTTP client, and Pytest.
- Install or verify Ollama on Windows.
- Pull and run the chosen Gemma 4B-class model.
- Record the exact model tag, quantization if applicable, Ollama version, and laptop performance.

**Acceptance**
- Backend starts locally.
- Ollama responds to a test prompt.
- No credentials or local data are committed.
- Setup instructions work from a clean checkout.

## Phase 1 — Typed Plan Contract

**Tasks**
- Define Pydantic models for task request, plan, action, validation errors, and task status.
- Support only a small allowlist of operations.
- Add a model adapter that calls local Ollama with timeout and error handling.
- Prompt Gemma to return structured plans.
- Validate model output; reject unknown actions and malformed fields.
- Keep planning read-only.

**Acceptance**
- Valid requests produce schema-valid plans.
- Invalid model output is rejected safely.
- Unsupported requests are declined or returned as needing clarification.
- No filesystem mutation occurs during planning.

## Phase 2 — Workspace and Permission Layer

**Tasks**
- Configure a dedicated test workspace.
- Resolve workspace IDs server-side.
- Implement path normalization and traversal checks.
- Define allowed operations and file-type restrictions.
- Add collision checks and source-state checks.
- Add tests for `..` paths, absolute-path injection, symlinks, nonexistent paths, and outside-workspace destinations.

**Acceptance**
- Requests cannot read or write outside configured workspaces.
- The backend—not the model or UI—enforces restrictions.
- Unauthorized and malformed requests fail closed.

## Phase 3 — First Working Automation

**Tasks**
- Implement directory scan with a bounded result size.
- Add deterministic file-type classification.
- Use Gemma only where semantic classification or naming suggestions add value.
- Implement a plan preview.
- Add approval state and an execution endpoint.
- Implement one mutation operation, preferably a safe move within the test workspace.
- Verify final source/destination state.

**Acceptance**
- No operation runs before approval.
- Existing destination files are not overwritten.
- Success is reported only after filesystem verification.
- Failures are recorded per action.

## Phase 4 — Action Ledger and Rollback

**Tasks**
- Create SQLite schema for tasks and actions.
- Record action state before and after execution.
- Store relative paths and sufficient rollback metadata.
- Implement undo for supported moves/renames.
- Check current state and destination conflicts before rollback.
- Record undo as a separate action/event.

**Acceptance**
- A supported move can be undone in the test suite.
- A rollback conflict stops safely.
- History remains intact after undo.
- Partial failures are represented accurately.

## Phase 5 — Duplicate Detection

**Tasks**
- Group candidates by size, then compare cryptographic hashes.
- Stream large files rather than loading them fully into memory.
- Report unreadable files and continue where possible.
- Display duplicate groups with paths and sizes.
- Do not delete duplicates automatically.

**Acceptance**
- Identical files are grouped correctly.
- Different files are not classified as exact duplicates based on name alone.
- No file is deleted.
- Errors are surfaced in the result.

## Phase 6 — Local-First and Offline Verification

**Tasks**
- Confirm inference uses the configured local Ollama endpoint.
- Audit application code for remote model API calls.
- Document network use for package/model downloads and optional features.
- Test core workflow after setup with remote model access disabled.
- Measure latency, RAM, VRAM, and failure behavior.

**Acceptance**
- Local inference is verified.
- Any network dependency is documented.
- Offline claims match test results.
- The selected model is usable on the target laptop or a smaller supported alternative is chosen.

## Phase 7 — Saved Workflows

**Tasks**
- Define a declarative workflow schema.
- Save workflow definitions in SQLite.
- Add manual rerun.
- Revalidate the workspace, permissions, and plan on every run.
- Track each run separately.

**Acceptance**
- A saved workflow can run again.
- It cannot expand its permissions by editing the request.
- Changed filesystem conditions are handled safely.
- Workflow history is available.

## Phase 8 — Recurring Scheduling

**Do only after Phase 7 is stable.**

**Tasks**
- Add a lightweight scheduler or operating-system integration.
- Add pause/resume/cancel controls.
- Decide whether each workflow requires approval at run time.
- Record each run and notify/report on failures.
- Avoid unattended destructive actions.

**Acceptance**
- Scheduled runs revalidate permissions and current state.
- Schedules can be stopped.
- Missed or failed runs are visible.
- No unsafe action silently bypasses approval.

## Phase 9 — React UI

**Tasks**
- Create a Vite React app.
- Add request input and task status.
- Render the plan and file paths.
- Add approve/cancel controls.
- Display action history, errors, and undo status.
- Handle API and Ollama unavailable states.
- Keep all enforcement in the backend.

**Acceptance**
- User can complete the MVP demo without calling APIs manually.
- The UI clearly differentiates proposed, approved, completed, failed, and undone actions.
- Errors are understandable and do not falsely show success.

## Phase 10 — Docker and Contributor Setup

**Tasks**
- Add backend Dockerfile and Compose configuration.
- Decide native versus containerized Ollama based on GPU testing.
- Mount only a dedicated workspace, never the entire home directory by default.
- Use non-root container settings where practical.
- Keep model data and SQLite persistence in documented volumes or host paths.
- Add health checks and configuration validation.
- Test from a clean environment.

**Acceptance**
- Documented setup starts the services.
- Host mounts are limited and intentional.
- No secrets are baked into images.
- Tests can run in the documented environment.

## Phase 11 — Test, Document, Demonstrate

**Tasks**
- Add unit tests for planning schemas, permissions, executor, ledger, rollback, and workflow validation.
- Add integration tests using a fake/mock model adapter where appropriate.
- Keep a smaller number of real-model tests for end-to-end validation.
- Test permission denied, collision, malformed model output, interrupted operation, and rollback conflict.
- Write architecture, security, setup, and troubleshooting docs.
- Record a short demo using sample files.
- Check licenses for source code, model, and dependencies.

**Acceptance**
- Test suite passes.
- README includes setup, supported features, limitations, and screenshots/demo.
- Claims about privacy, offline mode, performance, and reliability are supported by evidence.
- No personal files, tokens, or secrets appear in the demo or repository.

## Recommended First Vertical Slice

Build this before implementing the full roadmap:

1. Start FastAPI.
2. Send a natural-language request to Gemma via Ollama.
3. Receive and validate a plan for one test folder.
4. Preview one proposed move.
5. Require approval.
6. Execute the move through a restricted tool.
7. Verify the destination.
8. Store the action in SQLite.
9. Undo the move safely.
10. Run the tests.

Once this path works, expand the action catalogue and add the UI.

## Definition of Done for the MVP

- [ ] Gemma works through local Ollama.
- [ ] Plans are structured and validated.
- [ ] Workspace allowlist is enforced server-side.
- [ ] No arbitrary shell execution exists.
- [ ] At least one file operation requires approval.
- [ ] Operation result is verified.
- [ ] Action history is persisted.
- [ ] A supported operation can be undone.
- [ ] Exact duplicate detection works without deletion.
- [ ] Saved workflows can be rerun or are explicitly deferred.
- [ ] Tests cover security and failure paths.
- [ ] Docker/setup instructions are reproducible.
- [ ] README clearly states limitations and measured results.
